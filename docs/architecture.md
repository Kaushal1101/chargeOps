# 🏗️ LogiShield Pipeline Architecture

## Overview

LogiShield Pipeline is a real-time logistics risk detection system that simulates fleet telemetry, processes events as a stream, classifies operational risk, and generates AI-assisted remediation recommendations.

The platform follows an event-driven architecture with clear separation between:

- Telemetry generation
- Stream processing
- Risk detection
- Alerting
- AI-powered remediation

## Component Responsibilities

| Component | Responsibility |
|------------|----------------|
| Simulator | Generates realistic truck telemetry and anomaly scenarios |
| Kafka | Serves as the event bus between producers and consumers |
| Spark Streaming | Processes telemetry events and computes real-time metrics |
| Risk Tiering Engine | Assigns Green, Yellow, or Red risk levels |
| AI Agent | Generates business-impact summaries and mitigation recommendations |
| Chaos Injector | Simulates packet loss, latency, and degraded network conditions |
| Benchmarking Suite | Measures throughput, latency, and resilience |

---

## Data Flow

1. A telemetry event is generated by the simulator.
2. The event is published to the fleet-telemetry Kafka topic.
3. Spark Structured Streaming consumes and parses the event.
4. Rolling metrics are computed using event-time windows.
5. The risk tiering engine evaluates the shipment state.
6. Yellow and Red events are published to risk-alerts.
7. The AI remediation agent generates an operational recommendation.

## Kafka Configuration

### Topic Partitioning

Events are partitioned by `vehicle_id` using a hash-based strategy:

```
partition = hash(vehicle_id) mod total_partitions
```

This ensures all telemetry events for a given truck land on the same partition, preserving per-vehicle event ordering within the topic.

### Consumer Groups

Each consumer is assigned a dedicated group ID so Kafka tracks its offset independently:

| Consumer | Topic | Group ID | Offset Management |
|----------|-------|----------|-------------------|
| Spark Streaming | fleet-telemetry | `spark-fleet-processor` | Spark checkpoint directory |
| AI Agent | risk-alerts | `agent-alert-consumer` | Kafka-native (`auto.offset.reset=earliest`) |

Spark Structured Streaming manages its own offsets via a checkpoint directory rather than Kafka's native offset commit protocol. The group ID is still required for broker-side monitoring visibility.

The AI Agent uses `auto.offset.reset=earliest` so that on restart it replays any unprocessed alerts and never silently drops a risk event.

## Event Schema

The telemetry schema is shared across all services.

| Field | Description |
|---------|-------------|
| event_id | Unique event identifier (UUID v4) |
| event_ts | Event timestamp used for event-time processing |
| vehicle_id | Truck identifier |
| cargo_temperature | Current cargo temperature |
| time_left_to_destination | Estimated remaining travel time |
| sla_time_remaining | Remaining SLA buffer |
| scenario_state | Simulator injection state (GREEN, YELLOW, RED) — distinct from the risk_tier calculated by Spark |
| sla_buffer_threshold | Per-vehicle minimum acceptable delivery buffer in minutes |
| cargo_temp_threshold | Per-vehicle maximum acceptable cargo temperature in °C |

See [event_schema.md](event_schema.md) for full schema specification including derived fields and risk alert schema.

## Risk Model

Risk classification is deterministic and reproducible.

### 🟢 Green
- Truck operating normally
- Delivery buffer remains healthy
- Cargo conditions within threshold

### 🟡 Yellow
- Delivery buffer is shrinking
- Early warning indicators appear
- Potential SLA risk developing

### 🔴 Red
- High probability of SLA breach
- Cargo temperature violation
- Immediate operational intervention required

## Reliability & Fault Tolerance

The pipeline is designed to operate under imperfect network conditions.

### Event-Time Processing
Calculations are based on when events occurred, not when they arrive.

### Sliding Windows
Rolling aggregations enable trend detection instead of point-in-time analysis. Window size and slide interval are defined during implementation — see `spark_streaming/` for current values.

### Watermarking
Late-arriving events are handled gracefully without corrupting stream calculations. Watermark duration is defined during implementation — see `spark_streaming/` for current values.

### Chaos Engineering
Fault injection validates system behavior under packet loss, latency spikes, and burst traffic.

## Design Principles

- Event-Driven First — All major interactions occur through streaming events.
- Modular Components — Each service can be developed and tested independently.
- Deterministic Risk Detection — Risk classification remains explainable and reproducible.
- Stable Schemas — Shared event contracts across services.
- Observability by Default — Logging and benchmarking are first-class concerns.
- AI as an Enhancement Layer — AI explains and contextualizes risk; it does not replace core detection logic.

## Implementation Decisions

### OOP in the Simulator and Chaos Layer

`simulator/simulator.py` and `chaos/chaos_injector.py` are structured around classes with clear ownership boundaries:

- **`Scenario`** — resolves scenario state from a step counter and owns value generation for that state.
- **`Vehicle`** — encapsulates a single truck's identity, thresholds, and step-driven state. Exposes `generate_event(event_ts=None)` as the unified event construction method for both normal and chaos paths.
- **`Fleet`** — a collection wrapper with a `default()` classmethod. Does not own publishing.
- **`ChaosInjector`** — owns event timestamp transformation only (`apply_out_of_order`, `apply_delayed_burst`). Holds no fleet, producer, topic, or CLI state, making each chaos mode independently testable.

Run loops, the Kafka producer factory (`create_producer()`), and CLI entry points (`main()`) are kept as module-level functions. These are coordination concerns, not behavior that belongs on a class.

### Functional Style in Spark

`spark_streaming/stream_processor.py` is written in a purely functional style — a sequential chain of DataFrame transformations with no wrapping classes. Spark Structured Streaming is inherently functional: each operation returns a new DataFrame and the pipeline is expressed most clearly as a linear transformation chain. Adding a class would obscure the data flow without adding testability or isolation benefits.

### Chaos as Event Transformation

The chaos injector does not extend or modify vehicle or fleet behavior. Instead, `ChaosInjector` methods accept a `TelemetryEvent` and return a new `TelemetryEvent` with a modified timestamp. This keeps chaos logic isolated from simulation logic — the same fleet and vehicle classes power both normal and chaos runs without modification.
