# Phase 3A — Spark Ingestion Foundation

## Objective

Build the first Spark Structured Streaming application and verify that Spark can continuously consume telemetry events from Kafka.

This phase focuses only on ingestion and visibility.

No business logic, aggregations, windows, watermarking, or alert generation should be implemented yet.

---

# Scope

Included:

- Spark Structured Streaming setup
- Kafka integration
- Stream ingestion
- Console output
- Spark application deployment

Excluded:

- Risk tiering
- Derived metrics
- Windowing
- Watermarking
- Alert generation

---

# Architecture

```
Telemetry Simulator
      │
      ▼
Apache Kafka (fleet-telemetry)
      │
      ▼
Spark Structured Streaming (local mode, host machine)
      │
      ▼
Console Output
```

# Deliverables

## Stream Processor

Create:

```
spark_streaming/stream_processor.py
```

Responsibilities:

- Connect to Kafka
- Subscribe to fleet-telemetry
- Read telemetry continuously
- Display incoming records

---

## Kafka Connectivity

Spark connects to Kafka via the host-side listener:

```
localhost:9093
```

This is consistent with the Phase 1 decision: host-machine processes (simulator, scripts, spark-submit) use `localhost:9093`. Only processes running inside Docker containers use `kafka:9092`.

---

## Kafka Connector JAR

Spark cannot read from Kafka without the `spark-sql-kafka` connector. It must be passed at submit time via `--packages`:

```
org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1
```

This must be included in the `spark-submit` command. Omitting it causes a runtime failure when the Kafka stream is created.

---

## Raw Message Inspection

Display raw Kafka payloads to the console.

Do not parse JSON yet.

Do not apply schema yet.

The focus is simply: "Can Spark see the messages?"

---

## Starting Offsets

Set `startingOffsets` to `earliest`.

This ensures the job immediately consumes the existing backlog of messages in `fleet-telemetry` rather than waiting for new ones. Useful for validation — data will appear in the console immediately on startup.

---

## How to Run

The job runs in **local mode** via `spark-submit` on the host machine.

Command:

```bash
spark-submit \
  --master local[*] \
  --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1 \
  spark_streaming/stream_processor.py
```

Prerequisites:
- Docker stack running (`docker-compose up -d`)
- Simulator running (`python -m simulator.simulator`)
- venv active (`source venv/bin/activate`)
- `spark-submit` available on PATH (comes with a local PySpark install)

---

## Spark UI

In local mode, the Spark UI is available at:

```
http://localhost:4040
```

The streaming job should appear here as a running application. Note: `localhost:4040` is the local mode UI, not the Docker Spark Master UI at `localhost:8081`.

# Validation Checklist

- [ ] Spark application starts successfully
- [ ] Spark connects to Kafka via localhost:9093
- [ ] fleet-telemetry topic is consumed
- [ ] Incoming events appear in console output
- [ ] Streaming job remains stable
- [ ] Application visible in Spark UI at localhost:4040

---

# Exit Criteria

Phase 3A is complete when:

- A running Spark Structured Streaming job exists in local mode
- Telemetry generated by the simulator is visible in Spark console output
- Kafka → Spark connectivity is proven
- No ingestion errors occur

---

# Phase 3A Outcome

At the end of this phase, LogiShield will possess a verified streaming data path from Kafka into Spark.

Future phases can focus on analytics rather than infrastructure debugging.
